# Registry keypath fixture — second static checker

Root has built the original independent nonce fixture locally; its first static check failed because the table catalog included virtual _ForceCodepage metadata. This second tool does not rebuild or modify that MSI. It runs only read-only exports and static checks of the actual original artifact; no Windows install/query/uninstall has run. The PowerShell5.1 child is prepared source and has not been parsed or executed by PowerShell here. Production N/B frozen files are unchanged; `01`/`21` matching is not modified or guessed.

The fixture is independent of all production products: an explicit 32-lowercase-hex nonce derives separate Product/Upgrade/Component GUIDs under a fixture-only UUID namespace. Its sole effect is HKCU32 `Software\FutureClassroom-Test-RegistryKeyPath-<nonce>`, DWORD `OwnedMarker=1`, one component with registry KeyPath/Attributes4. It is per-user x86 MSI500, with one feature, no installed files, no CA/Binary/Run/service/environment/upgrade handoff, no production helper and no gate/Pending. Ordinary MSI `/x` remains available even if a production helper would retain Pending.

After root supplies a nonce, `registry-fixture.py --nonce <32hex> describe` prints exact GUID/key/value metadata only. `... author --output-dir <fresh-owned-directory>` creates WXS and `fixture-spec.json`, not MSI. Root uses the already reviewed R75 tool closure (no new downloads, installation or global environment):

```text
child LD_LIBRARY_PATH=/tmp/fc-round75-installer-maintenance/tools/root/usr/lib/x86_64-linux-gnu
/tmp/fc-round75-installer-maintenance/tools/wrappers/wixl -a x86 -o fixture.msi fixture.wxs
```

Run that command with the new authoring directory as cwd and retain actual stdout/stderr/exit/SHA. Then retain original `msiinfo suminfo`, `msiinfo tables`, and an original IDT export for every non-system listed table. `registry-fixture.py --nonce <same nonce> check-exports --exports <idt-directory> --tables-list <raw-list-file> --summary <raw-summary-file>` requires exact Property/Directory/Component/Registry/Feature/link/launch-condition rows, formal registration+removal sequencing, no custom action or external upgrader and no unknown nonempty effects table. A strict checker refusal on real tool output is evidence to inspect, not a reason to skip checking. Bind source WXS/spec, tool identities, actual MSI bytes and all exports in the root controller before Windows operations. No cached installer file is hand-edited or deleted.

Root alone performs the finite Windows lifecycle, first preflighting the explicit identities:

1. Create a unique owned report root whose basename is `FutureClassroom-r75-registry-keypath-<nonce>` and `.owner` bytes are exactly `future-classroom-owned-r75-registry-keypath/v1` plus LF. Copy the original query script/spec into root-owned locations, pin their SHA, and reject any pre-existing fixture product/context/related registration or HKCU32 key. Production Run, target and Pending are read-only observations, never touched by this fixture.
2. In an original **x86 Windows PowerShell5.1** child, run `query-registry-x86.ps1 -Phase Before -SpecPath <spec> -ExpectedSpecSha256 <sha> -OutputRoot <ownedroot>`. On 64-bit Windows choose `SystemRoot\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`; on x86 Windows use System32. Launch with `-NoProfile -NonInteractive -ExecutionPolicy Bypass -File <script>` in a bounded parent process, capture original stdout/stderr, and require actual exit0 plus `Before.json` exact absence. No fake caller bitness field substitutes for the script's actual Is64BitProcess check. The script sets TMP/TEMP only within this child to a fresh phase-specific owned subtree before Add-Type.
3. Run the exact admitted fixture using original engine `msiexec /i <fixture.msi> /qn /norestart /L*v <unique-install-log>`. No transforms or public override properties. Record actual process return and elapsed time, then Phase Installed in a new original x86 child. It calls `MsiGetComponentPathExW` and `MsiGetProductInfoExW(VersionString)` in actual contexts1/2/4, with current user SID or NULL for machine; preserves integer codes, component state, full original UTF16 keypath string/hex, and OS/process bitness. Expected present means current-user unmanaged context2, version0.0.1 and component LOCAL, plus exactly the one DWORD marker. It does **not** assert a `01` or `21` prefix.
4. Whether the installed observation succeeds or fails, root's `finally` attempts **formal original-engine `/x <fixture ProductCode> /qn /norestart /L*v <unique-uninstall-log>`** for this preflight-proven owned fixture. Do not bypass hooks, transform a package, use Remove-Item on installer registrations or erase cached MSI files to manufacture cleanup. Phase After must show exact key absent, no related product, product UNKNOWN1605 and component UNKNOWN in all three queried contexts. Raw statuses remain original if anything differs. Uninstall is a separate actual result from measurement success.
5. Physically reap original engine/query/compiler processes; retain all reports/logs; only then remove this nonce's owned report/query-temp/authoring artifacts. Preserve all production state, school data, Run values, persistent SSH/key and unrelated fixtures. If engine cleanup is not proved, retain the owned fixture and report failure rather than hand-delete registration.

Proposed finite root-controller budget is one original 120-second origin for this small fixture lifecycle: each query child at most10s, each engine command at most45s with reserved formal cleanup time, no deadline renewal. Root may choose a stricter explicit schedule before execution; no budget or actual runtime is claimed here. Parent timeouts apply to the original owned process handles and retain failure evidence. A single x86 query only proves the observed OS/account/context; Win7/10/11 and standard/elevated routes remain separate.

Microsoft documents numeric registry roots and a 64-bit OS distinction, while this test deliberately retains the actual returned string instead of resolving that wording by assumption: [MsiGetComponentPathExW](https://learn.microsoft.com/en-us/windows/win32/api/msi/nf-msi-msigetcomponentpathexw). Product context and unknown-product codes are recorded independently: [MsiGetProductInfoExW](https://learn.microsoft.com/en-us/windows/win32/api/msi/nf-msi-msigetproductinfoexw). The last authored registry value can be removed by normal component uninstall without a destructive remove-key wildcard: [Registry table](https://learn.microsoft.com/en-us/windows/win32/msi/registry-table).

Second correction is based on actual exports and upstream implementation, not a pure-model promotion. Original MSI SHA is d3c6d5e4937d5dd673e9835a7fbc8d5c7d03af8b0527e1a12d565da1a0e4e248. Root first result/tool remain immutable. Actual `_ForceCodepage` export bytes are exactly two CRLF empty lines, `0\t_ForceCodepage\r\n` and terminal NUL. The v0.103 exporter writes that terminator and obtains the database string-table codepage. This is virtual metadata, not an effects table. The second checker requires this exact neutral0 representation and every actual exported table entirely ASCII. It does not skip arbitrary underscore tables or accept unknown nonempty effects. An additional read-only `_SummaryInformation` export reports PropertyId1=1252; this is summary codepage, distinct from StringPool neutral0. No string-pool1252 claim is made and the MSI is not imported/converted/rebuilt.

Actual wixl0.103 AdminExecuteSequence includes standard InstallAdminPackage at3900 with empty condition. The second checker admits exactly that row only in AdminExecuteSequence. The ordinary install/remove execute actions, eight core tables, all other conditions, no CA/Binary/File/Run/Upgrade rules and unknown-nonempty rejection remain unchanged. Every other actual nonempty table matched the first intended contract.
