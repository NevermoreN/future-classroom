# Parent-engine SID deployment premise: read-only probe design

Current `Session::engine` pins the actual parent process, requires the actual System32/SysWOW64 msiexec image and compares that parent's primary TokenUser with helper SID. This guard is unchanged. Official documentation says default custom actions have user privileges and execution can switch to the server after InstallValidate. It does not guarantee that the creating process has the same primary SID as the child. Type2 documentation describes CreateProcessAsUser/CreateProcess for scripted EXEs, and CreateProcessAsUser can select a child security context separately. These facts support uncertainty, not a proven failure of the current immediate Type2 route. R60's guardian SID does not establish the Begin parent's SID. [Security](https://learn.microsoft.com/en-us/windows/win32/msi/custom-action-security), [sequencing](https://learn.microsoft.com/en-us/windows/win32/msi/sequencing-custom-actions), [Type2](https://learn.microsoft.com/en-us/windows/win32/msi/custom-action-type-2), [process creation](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes)

Do not loosen equality to allow SYSTEM on speculation, do not supply a parent PID/SID over wire, and do not run the real product Begin to discover the context: it can create Pending.

Proposed independent test-only probe (requires root/N authorization before adding code):

- Compile a cfg(test)-only read-only observer in the existing native test artifact. No observer role in normal helper; no call to LifecycleResources, gate acquisition, Pending, registration, file installation, registry mutation or transaction join/end. Use isolated random test ProductCode/UpgradeCode unrelated to the product.
- Package a tiny no-payload test MSI with only the exact observer Binary/Type2 action at1499 condition1. Put Type19 forced abort at1500 and explicit InstallInitialize at1501. Keep CostFinalize1000/InstallValidate1400 beforehand. Actual exported tables must prove abort < Initialize and no File/Registry/Run/service/RemoveExistingProducts effects. This preserves the relevant afterValidate context while preventing transaction initialization.
- Observer derives its real parent via kernel/snapshot relationship and immediately holds/query-validates process object/creation time. Read own primary TokenUser, optional current thread impersonation token, parent TokenUser, parent image and creation, observed process/session IDs and integer OS errors. Missing thread token is a typed observation, not automatic failure. Query actual image identity; never accept a caller-supplied parent field as evidence.
- Write one bounded report with create-new semantics only in an independently marked owned temporary root with checked ownership/path and no inherited write capability to product locations; all handles explicitly close. No credentials, environment dumps or arbitrary process command lines. Preserve exact source/binary/MSI hashes and actual process metadata. Observer reports facts and never grants product admission.
- Root runs separate actual quiet/basic/full UI and unelevated/elevated/standard-user cases on authorized OS targets. Every case expects observer0 followed by the deliberate Type19 failure (normally1603), then verifies no original product/root/marker/Run/Pending change and no test product/context registration. Record actual UI level and MSI log sequence. Full UI requires controlled dismissal of the owned test popup. Parent process return and all owned children must be physically reaped before cleanup. Engine temporary extraction/log activity is recorded and is not claimed to be zero system activity.
- If the observed parent is SYSTEM while the helper's TokenUser is the interactive user, current strict equality would reject that legitimate deployment route. Bring the actual evidence back for authenticated engine/session binding design; do not merely allow SYSTEM. If equality holds in one case, that proves only that observed route/OS/UI/elevation combination, not universal support.

This file is a proposal; no probe source, MSI, process or Windows operation was produced/executed here.
