# Same-manifest maintenance: B-side read-only candidate

Status: design only. Frozen B7/N3 sources unchanged. No Cargo, MSI construction, Windows execution, product installation, Run edit, or main edit in this task. Repair/uninstall are not implemented or validated by this document.

## Smallest honest capability

Keep the existing closed role grammar, v1 overlay, fixed KnownFolder root, single original 120-second deadline and 64-handle/8-owner accounting. Begin remains condition `1`, Type2, sequence1499, target `begin "[FcInstallDir]fc-bootstrap.exe"`; CostFinalize1000 and InstallValidate1400 precede it, InstallInitialize1500 and every mutation follow. Rollback/commit notices remain advisory. Do not add intent arguments, public permission properties or caller `effects_reconciled`.

A proposed neutral same-manifest maintenance admission can permit both reapplication and full removal without trusting REMOVE/Installed/CLI intent: under the real exclusive gate, independently verify same ProductCode/version/current per-user context, same original trusted manifest, no conflicting related product, exact payload/hash/membership/markers/component registrations/fixed root, and absence of the project's HKCU Run value. The first bounded slice admits an intact baseline only. Reapplying an intact package is not evidence of repairing missing/corrupt files. Supporting damaged repair needs a separate bounded preimage and rollback policy; reject foreign or mixed state before mutation.

Staged full files+markers can be a repair candidate; staged complete absence can be a full-removal candidate. Do not require post-transaction Product registration absence while the transaction is still active: check actual registration after End and the original guardian's physical exit. Partial/mixed/unknown effects must not authorize commit. Settlement requires successful real transaction end, original guardian exit0, independent final full or complete-absence proof, and rollback restoration of the captured admitted preimage. Release file pins before mutation/end when required for MSI DELETE rights; native ownership/watch strategy must still detect intervening changes. These are N-owned design requirements, not behavior already present.

Scope is the controlled original candidate without TRANSFORMS, tested through genuine install/reapplication/uninstall routes. Type2 EXE has no MSI installation-session handle; offline exact-table validation proves the built artifact and does not authenticate arbitrary effective transformed sessions. Do not call a CLI claim of TRANSFORMS absence an authority. This is a capability boundary, not a newly imposed arbitrary-hostile-MSI/no-side-effects requirement. No D11 text establishing that broader requirement was identified in this review. Parent explicitly deferred a new DLL artifact; the bounded next slice needs no DLL. Own controlled related-package admission can reject its major upgrade without claiming control of arbitrary external upgrade initiators.

## Folder and registry effects

Current File/Directory authoring lacks explicit CreateFolder/RemoveFile rows. This is NOT a proven cleanup defect: Microsoft explicitly documents automatic removal when installer-created folders not listed in CreateFolder become empty. Therefore the minimal proposal keeps existing tables and first measures actual nested program-root absence after uninstall and fresh rollback. [CreateFolder table](https://learn.microsoft.com/en-us/windows/win32/msi/createfolder-table)

If actual evidence requires explicit folder ownership, a bounded alternative is manifest-derived CreateFolder rows for only FcInstallDir and its actual validated descendant directories, associated with the stable existing main-file component; retain original component GUID/key path. Add exact CreateFolders3700 and RemoveFolders3600, after RemoveFiles3500. The checker must admit precisely those rows, while keeping RemoveFile and RemoveRegistry forbidden. RemoveFolders removes only empty owned folders. Never extend to LocalAppData, Programs, coordinator namespace or school data. Table row order is not evidence that nested cleanup succeeded. [RemoveFolders](https://learn.microsoft.com/en-us/windows/win32/msi/removefolders-action), [standard sequence](https://learn.microsoft.com/en-us/windows/win32/msi/suggested-installexecutesequence)

Existing exact GUID DWORD1 Registry rows should remove their own marker key when its last value/subkey is removed; measure actual absence. Do not use Registry Name `-`/`*`, which would delete unrelated children, nor manually erase registry/MSI caches to manufacture success. [Registry table](https://learn.microsoft.com/en-us/windows/win32/msi/registry-table)

Uninstall success scope: fixed program namespace absent, own marker namespace absent, exact Product/context/component registrations absent, no unrelated effects. The separate coordinator namespace contains gate.lock and is currently persistent; deleting it after releasing the gate risks a replacement-owner race. Do not claim it is already removed or manually delete it as MSI cleanup. Native identity-safe retirement would require a separate design. Capture LocalPackage/SourceList state read-only, leave installer-owned cache management to MSI. Never delete cached MSI files/registration, apply transforms, disable lifecycle hooks or use hand cleanup as the uninstall proof.

Project Run guard concerns only value `FutureClassroom` in HKCU Software\Microsoft\Windows\CurrentVersion\Run. The whole Run key belongs to other apps too. Future maintenance must reject a present project value before mutation, retain unrelated Run sentinels and leave all existing values unchanged. This slice does not implement Run migration/removal, major upgrade, school-data or ProgramData changes.
